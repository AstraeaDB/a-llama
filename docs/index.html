A gentle introduction

If you've used Ollama, you already know a-llama's starting point: run a local LLM, talk to it over a simple HTTP API, no cloud required. a-llama speaks that same API — so existing Ollama clients, scripts, and SDKs can point at it unchanged — but it adds one thing Ollama doesn't have: a memory that grows. Ollama answers your question and forgets it. a-llama answers, remembers, and gets more useful the more you use it — without ever retraining the model.

The trick isn't magic and it isn't fine-tuning. Every exchange is embedded and stored — in a fast semantic cache for "have I seen this before?", and in an embedded knowledge graph for the long haul. When a new question arrives, a-llama quietly looks up what it already knows that's relevant and folds it into the prompt before the model answers. Turn on durable mode and that memory is written to disk, so it's still there after a reboot. It all runs in one process — the model, the database, and the vector search — with no servers to deploy.

What it can really do

  • Be a drop-in local LLM server. Point any Ollama-compatible client at it for generate, chat, and embeddings.
  • Remember across questions — and restarts. Repeat or rephrase something and it's served from memory (in our test, ~15× faster); with durable mode that memory survives a process restart.
  • Learn facts as you talk. With extraction enabled it distills facts and named entities from conversations into a knowledge graph you can actually inspect.
  • Use what it learned to answer better. A later, differently-worded question pulls the relevant stored knowledge back into the prompt (GraphRAG) instead of starting from scratch.
  • Run entirely offline and embedded. Single binary, in-process database, no network for storage — suitable for air-gapped or privacy-sensitive use.
Honest framing. a-llama is "Ollama plus an embedded learning memory." The quality of answers and extracted facts tracks whichever GGUF model you load — a tiny model is crude, a stronger one is much better; what a-llama adds is the durable, retrievable memory around it. It runs one model at a time and targets the common Ollama verbs (not yet the full model-management surface — see the roadmap).

Sample use cases

🧠 A local assistant that remembers you

Use a-llama as the backend for your chat or coding tool. Tell it your stack, conventions, and preferences once; with durable mode on, it recalls them tomorrow after a reboot — no re-explaining, no fine-tuning job.

📓 A notebook that answers back

Turn on fact extraction and just talk to it about a project, a codebase, or your research. It builds a knowledge graph as you go, then surfaces the right facts when you ask a related question later — a self-building knowledge base from plain conversation.

⚡ A semantic cache for an LLM

Put a-llama in front of an FAQ, support, or docs bot where people ask the same things many ways. Semantically-equivalent repeat questions come back from cache in ~0.1 s with the same answer — cheaper and faster than regenerating every time.

🔒 An offline / private assistant

One binary, no server, no cloud, no network for storage. Drop it into a desktop app, an edge device, or an air-gapped environment where data can't leave the machine — model, memory, and search all live in-process.

🔬 A continual-learning testbed

Researching "can an LLM keep learning without retraining?" a-llama is a working harness: the learn→store→retrieve→augment loop, durable memory, and an inspectable knowledge graph. Swap the model, tune retrieval, measure.

Ready to try it? Jump to Build & run — the default build boots instantly with a built-in mock engine; add a GGUF model when you want real answers.

Overview

a-llama is a single binary: a local LLM inference daemon that speaks an Ollama-compatible HTTP API to client tools, with AstraeaDB (graph + vector store) and Eunomia (semantic cache) compiled in-process as its memory subsystem. There is no separate database server and no network daemon for storage.

Its differentiator is continual learning by retrieval-augmentation: rather than updating model weights, a-llama persists what it sees — interactions, distilled facts, linked entities — into its embedded knowledge graph and semantic cache, then feeds that knowledge back into future prompts. With durable persistence enabled, what it learns survives a process restart: a question answered in one process is recalled instantly by a fresh process from the same data directory — continual learning without retraining.

Verified live. Running the real engine (mistral.rs qwen2.5 chat + embeddinggemma 768-dim embedder), a question answered in 10 s in one process is recalled in 0.10 s by a fresh process from the same A_LLAMA_DATA_DIR after a restart.

The two meanings of "embedded"

These are deliberately kept separate (design decision 7657):

AstraeaDB is embedded

Linked as an in-process library (astraea-graph::Graph) — no separate Astraea server, no ports, no network. This is the project's "embedded" constraint.

a-llama is a local daemon

a-llama itself does expose an HTTP API over axum + tokio. That local API is the product — the drop-in Ollama replacement. It is not an Astraea network surface.

Everything in the box is one process. The inference engine is swappable (MockEngine for tests/default, mistral.rs for the real backend). The long-term store can be in-memory (default) or durable (DiskStorageEngine).

The continual-learning loop

Each request runs learn → store → retrieve → augment:

  1. Embed the incoming prompt (768-dim, the in-process embedder).
  2. Retrieve (hot) — probe the Eunomia SemanticCache; a high-similarity hit can short-circuit to the cached response.
  3. Augment (long-term) — on a miss, run a GraphRAG query over the learned knowledge graph: vector search → subgraph (BFS) expansion → linearize → splice the context into the prompt.
  4. Infer — the engine generates from the augmented prompt.
  5. Learn / store — write the interaction to the hot cache (with TTL).
  6. Tier — evicted cache entries are flushed into the durable graph as retrievable CacheEntry nodes.
  7. Extract (opt-in) — an LLM pass distills Fact/Entity nodes + edges so individual facts become independently retrievable.

Over time the graph accumulates the model's "experience," and step 3 surfaces it back.

KnowledgeStore

Wraps an in-process astraea_graph::Graph with an attached ExactVectorIndex pinned to 768-dim. Three node kinds and three edge types form the schema:

(Fact {text, source_id, confidence, created_at, embedding})
   ─DERIVED_FROM─► (CacheEntry {eunomia_id, value, tags, …, embedding})
   ─MENTIONS─────► (Entity {name, kind})
(Entity) ─RELATES_TO─► (Entity)

The upsert_cache_entry / upsert_fact / upsert_entity methods are true upserts (dedup by stable key: namespace+eunomia_id, source_id+text, kind+name) — re-flushing the same item updates in place. Every embedded node is indexed for vector search and reachable by GraphRAG.

ExactVectorIndex

An exact (brute-force) implementation of astraea_core::VectorIndex used by the KnowledgeStore: every search computes the distance to every stored vector and returns the k closest, so recall@k = 1.0 by construction — the knowledge graph always retrieves the genuinely nearest learned items. Distances use astraea_vector::distance::compute_distance, and O(N·dim) is sub-millisecond at every graph size a-llama realistically reaches.

Inference engine

InferenceEngine is the swappable seam (async complete + embed):

  • MockEngine — deterministic, dependency-free; canned completions and stable 768-dim pseudo-embeddings. The default build and all tests use it.
  • MistralRsEngine (feature mistralrs-engine) — real mistral.rs 0.8 backend: a GGUF chat model + an embeddinggemma embedder. The embedder is forced to F32 (it returns all-zeros under the default F16 on CPU) and its output dimension is probed and required to be 768 at load.
  • EngineProvider — adapts any engine to astraea_rag's synchronous LlmProvider + EmbeddingProvider for GraphRAG, bridging async→sync via block_in_place (hence the multi-thread runtime requirement).

Augmenter (GraphRAG)

Drives astraea_rag::graph_rag_query over the KnowledgeStore + EngineProvider: embed the question → vector-search an anchor node → BFS-expand the subgraph → linearize to text under a token budget → assemble the augmented prompt. Must run on a multi-thread Tokio runtime.

SemanticCache

Wraps eunomia_core::Store as the hot prompt→response cache: lookup (threshold-gated nearest-neighbour, TTL-filtered), store_interaction (stable id, TTL), sweep_expired. In durable mode it recovers from a WAL + snapshot.

Fact extraction

Opt-in (A_LLAMA_EXTRACT_FACTS=1). On a cache miss, an extra LLM pass over the prompt→response exchange emits JSON that a tolerant parser turns into Fact/Entity nodes + edges. It runs detached (never blocks the HTTP response) and errors are swallowed. Quality scales with the chat model.

Orchestrator

AppState holds the engine, the shared KnowledgeStore (also used by the Augmenter), and the SemanticCache behind a lock. generate() runs the full loop; tier_evicted() flushes evicted entries; persist() writes durable state. The router exposes the Ollama API.

Build & run

Default (mock engine, in-memory) — instant

cargo run --release
# → a-llama listening on http://127.0.0.1:11434 (model: mock-gguf)

Real engine (mistral.rs)

cargo build --release --features mistralrs-engine

A_LLAMA_ENGINE=mistralrs \
A_LLAMA_GGUF=/abs/path/to/model.gguf \
A_LLAMA_EMBED_MODEL=google/embeddinggemma-300m \
  ./target/release/a-llama
# Needs an HF token at ~/.cache/huggingface/token (embeddinggemma is gated).

Durable (survives restart)

cargo build --release --features durable          # or: mistralrs-engine,durable
A_LLAMA_DATA_DIR=/var/lib/a-llama ./target/release/a-llama
# Ctrl-C / SIGTERM flushes graph + cache to disk; next start replays them.

Fact extraction

A_LLAMA_EXTRACT_FACTS=1 ./target/release/a-llama

Durable persistence

With --features durable + A_LLAMA_DATA_DIR:

  • Graph → DiskStorageEngine (WAL replay on open; ids resume via Graph::with_start_ids).
  • Vector index → the ExactVectorIndex is rebuilt from the persisted node embeddings on open (no index file to corrupt).
  • Dedup indexes → reconstructed by walking the persisted nodes.
  • Cache → Eunomia recovers from a WAL + snapshot (puts are logged before apply; evictions logged as deletes).
  • Shutdown → a SIGTERM/SIGINT handler calls persist() (flushes the buffer pool + cache snapshot).

On-disk layout: <dir>/graph/astraea.db, graph/astraea.wal, cache.snap, cache.wal. Requires astradb ≥ 0.1.11 (overflow records + WAL append fix).

#Decision
7659Swappable InferenceEngine trait; mistral.rs default, llama-cpp-2 as a future fallback.
7660Embedding model = embeddinggemma, dim 768 — pinned across cache, graph index, and embedder.
7657Two distinct "embedded" meanings: embedded AstraeaDB library vs a-llama's own HTTP daemon.
7658AstraeaDB crate set: core, graph, vector, rag (+ storage behind durable); exclude server/flight/mcp/cluster.
2145Durable tiering is native (flush into a-llama's own graph) — not the eunomia-astraea bridge (it owns a separate graph).

Status & roadmap

Feature-complete. M1 (daemon) + M2 (tiering, durability, extraction, tests) + the real engine are all done, committed, and live-verified.

The optional roadmap lives in NEXT-SESSION.md, prioritized:
